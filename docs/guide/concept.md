## ひとことで言うと

**人（体制）・モノ（成果物）・金（予算）を、1つのデータの上で同時に見るためのツール**です。

タスクを1つずつ進める道具ではありません。
「このままで予算に収まるのか」「誰かに無理が乗っていないか」「削るならどこか」を
**判断するための道具**です。

前提となる考え方は [プロジェクト管理の基礎](project-management.md) にまとめました。
QCDや人・モノ・金という言葉に馴染みがなければ、先にそちらをご覧ください。

---

## 1. 解こうとしている問題

プロジェクトが傾くとき、多くの場合それぞれの情報は**どこかには存在しています**。

- 体制は、PMのExcelに
- 進捗は、Backlogに
- 予算は、経理から送られてくる月次の資料に

問題は、これらが**別々の場所にあって、突き合わせないと状況が分からない**ことです。
突き合わせは手作業なので、頻繁にはできません。だいたい月1回、会議の前日に、
誰かが徹夜でExcelを作ります。そして会議が終わると、その数字は次の月まで更新されません。

そのあいだに状況は動きます。
気づいたときには、予算が尽きていたり、特定の人に3案件ぶんの仕事が乗っていたりする。

**triplanは、この突き合わせを無くすために、3つを同じデータモデルの上に置きます。**

WBSの工数を直せば概算予算が変わる。アサインを動かせば人件費の実績とEVMが変わる。
変更請求を承認すれば受注額と納期が変わる。**転記が要りません。**

## 2. 何をして、何をしないか

「餅は餅屋」を設計方針にしています。何でもできるツールを目指すと、
どの機能も中途半端になるためです。

### する

| | 何ができるか |
| --- | --- |
| **体制を組む・見る** | 誰がどの案件に何割いるか（月単位）。時短・兼務の稼働率上限も加味した山積み。無理が乗っている人は警告で分かる |
| **スコープを分解する** | 案件を最大5階層のWBSへ。工数を積み上げて概算予算を出す。「この機能を削ったらいくら減るか」の試算（What-if） |
| **予算の予実を追う** | 部門予算・案件別収支・原価4区分（労務費／外注費／直接経費／間接費配賦）・AI利用費・SaaS契約 |
| **進捗と予算のズレを見る** | EVM（予定・出来高・実コストの3本線）。SPI/CPIで「遅れ」と「使いすぎ」を分けて把握 |
| **商流を追う** | 受注額・請求マイルストン（予定→検収済→請求済→入金済）・変更管理（CR承認で受注額と納期に自動反映） |
| **月次で締める** | 実績の確認・確定・締め。締めた月は変更できない（解除は理由必須で証跡が残る） |
| **外部へ渡す** | 支払明細・請求データ・案件別収支をCSVで。列の並びと名前は外部システムに合わせて設定できる |

### しない

| | 委ねる先 | 理由 |
| --- | --- | --- |
| **日々のタスク実行管理** | Backlog / Asana / Jira / GitHub | カンバン・コメント・通知は専門ツールの方が優れている。**連携して繋ぐ**（WBSから一括起票し、完了は自動で戻る。API連携はpostgresモード専用で、localモードはCSVの受け渡し） |
| **勤怠・工数の打刻** | 勤怠システム | triplanが扱うのは月単位の「人月」。分単位の打刻は目的が違う |
| **会計処理・請求書の発行** | 会計ソフト / 請求書サービス | CSVで渡す形にする。帳票の体裁を作り込むのは専門ツールの仕事 |
| **チャット・議論** | Slack / Teams など | 通知は送るが、会話はしない |

この線を引いているので、**triplanだけで完結はしません**。
既存のタスク管理ツールを捨てる必要もありません。むしろ併用が前提です。

## 3. QCD・人モノ金と、画面の対応

[プロジェクト管理の基礎](project-management.md) で見た枠組みが、どの画面に対応するかです。

| 軸 | 見たいこと | 主な画面 |
| --- | --- | --- |
| **人**（体制） | 誰がどれだけ関わるか / 誰に無理が乗っているか | [チーム](planning.md)・[アサイン](planning.md)・ダッシュボードの山積み |
| **モノ**（成果物） | 何をどこまで作るか / どこまで終わったか | [プロジェクト・WBS](planning.md)・[スケジュール](planning.md) |
| **金**（予算） | いくら使えるか / いくら使ったか / 儲かっているか | [予算管理](budget.md)・[月次明細](commerce.md)・案件別収支 |
| **Q**（品質・スコープ） | 削るならどこか | WBSツリー・What-ifシミュレーション |
| **C**（コスト） | 予算に収まるか | 予算管理・EVMのAC・案件別損益 |
| **D**（納期） | 間に合うか | スケジュール・EVMのSPI・アラートセンターの遅延予測 |

### 3軸を1画面で見る場所

軸ごとの画面を見比べるのは手間なので、集約した画面が2つあります。

- **[プロジェクトサマリー](budget.md)**（`/project-summary`）——
  1案件の健全性を1分で確認する読み取り専用ページ。
  8つの決定論的なルール（納期超過・遅延予測・予算超過・予算先行・SPI低下・
  ベースライン乖離・配分ギャップ・稼働超過）で総合判定を出し、
  金／モノ／人／商流の4区画を1画面に並べます
- **ダッシュボードのアラートセンター**（`/dashboard`）——
  全案件を横断して、重大度順に「見るべきもの」だけを並べます。
  毎朝ここだけ開けばよい、という位置づけです

## 4. 向いている場面・向いていない場面

### 向いている

- **複数の案件を並行して回している** — 1人が複数案件を掛け持ちしていて、
  誰にどれだけ乗っているか把握しきれていない
- **協力会社を含む体制** — 自社と外注で単価が違い、支払と請求の両方を管理する必要がある
- **予算と体制を同じ人が見ている** — 部門長・PMなど、金と人の両方に責任がある立場
- **年度で予実を締める** — 年度単位の予算があり、月次で実績を確定させる運用がある

### 向いていない

- **1案件・数人で、期間も短い** — Excelで足ります。導入コストの方が高くつきます
- **タスクの実行管理だけしたい** — Backlog / Asana などの方が適しています
- **個人のタスク管理** — 用途が違います

> 迷ったら、**デモデータで試してから**判断してください。
> 空の状態でダッシュボードを開くと「はじめに」カードが出るので、
> 「デモデータで試す」を選ぶと一式のデータが入ります
> （[はじめに](getting-started.md)）。

## 5. 設計の考え方（なぜこうなっているか）

操作していて「なぜこうなっているのか」と思ったときの答えです。

### 入力を増やさない

管理のための入力作業が増えると、続きません。
そこで、**普段の作業から自動で導出できるものは、入力させない**方針をとっています。

代表例がEVMです。3つの指標のうち、

- **予定（PV）** — 計画を「凍結」したときのアサイン配分から
- **出来高（EV）** — WBSの完了チェックから（EVMが無くてもやる作業）
- **実コスト（AC）** — アサイン表と単価から

を自動で算出します。EVM専用の入力はありません。PMがやるのは「計画の凍結」だけです。

### 記録は消さない

締め・解除、変更請求の承認、監査証跡（postgresモード）は、
**追記のみ**で、後から書き換えられません。
「いつ・誰が・なぜ変えたか」が残らないと、数字を確定させる意味がなくなるためです。

### 既存のデータを勝手に上書きしない

CSV一括登録は、既存と一致した行を**取り込まずに理由を表示**します。
移行のつもりで実行したら現行データが書き換わっていた、という事故を避けるためです。
適用前に必ず「登録される内容」をプレビューで確認できます。

### 金額は立場によって隠す

協力会社のメンバーにも進捗や体制は見せたい。でも単価や利益は見せられない。
そこで**金額を含む画面・区画だけを隠す**仕組みを持っています。

- 予算管理・月次明細は**画面ごと**閉じる
- プロジェクトサマリーは**区画単位**（金・商流だけ消え、進捗・体制は残る）
- サイドバーの金額系メニュー、レポートの金額帳票も消える

postgresモードは権限（`financials:read`）で自動、localモードは全社設定の表示トグルです。
[権限とシステム設定](admin.md) を参照してください。

## 6. 案件を1本、最初から最後まで回す

機能の一覧を見ても、どこから手を付けるかは分かりません。
**1つの案件が引合から締めまで進む流れ**に沿って並べ直すと、
それぞれの画面が何のためにあるのかが見えます。

```
  初回だけ  │            案件ごと              │        毎月
 ──────────┼─────────────────────────────────┼──────────────
            │                                  │
  ┌──────┐  │  ┌──────┐    ┌──────┐  ┌──────┐  │  ┌──────┐
  │ 準備 │ ─┼→ │ 引合 │ ─→ │ 計画 │→ │ 実行 │ ─┼→ │ 月次 │
  └──────┘  │  └──────┘    └──────┘  └──────┘  │  └──────┘
  組織・人  │  案件登録    WBS精緻化  外部ツール │  確定・締め
  単価      │  粗いWBSで   体制・凍結  へ起票    │  報告
            │  概算            ▲       完了が戻る│     │
            │              受注確定    　        │     │
            │                  └─── 調整して再凍結 ────┘
```

| # | やること | 画面 | 補足 |
| --- | --- | --- | --- |
| **準備（初回だけ）** | | | |
| 01 | 組織と人を登録する | チーム／管理画面のCSV一括登録 | 単価は2種類（見積用の「単価」と、協力会社への実支払い用の「契約単価」）。人がいないとアサインできないので案件より先 |
| **引合（案件ごと）** | | | |
| 02 | 案件を登録する | プロジェクト | まだ受注前でよい。確度（S/A/B/C）で温度感を持たせる。見込み段階から入れておくと、要員の取り合いが事前に見える。WBSを切る前の超概算は「見積」画面の簡易FPで出せる（[見積と不確実性コーン](estimation.md)） |
| 03 | WBSを粗く切って概算を出す | WBS | 標準テンプレートを当てて大づかみの工数を入れる。**工数 × 概算単価 × 係数 = 概算予算額**が自動で出て、これが見積の根拠になる。「見積」画面で段階（受注時＝製品定義、要件確定後＝要件定義完了）を付けて記録しておくと、後から実績との誤差を振り返れる |
| **計画（受注が決まったら）** | | | |
| 04 | WBSを精緻にする | WBS | 数日〜2週間の大きさまで分解し、完了条件を書く |
| 05 | 工程に日付を入れる | スケジュール | ガントで工程の期間を引き、タスクを工程へ紐づける。紐づけるとタスクの期日が工程の終了日から決まり、バーに完了状況が乗る |
| 06 | 体制を組む | アサイン | 誰が何月に何割。山積みで無理が見える |
| 07 | 計画を凍結する | WBS「計画を凍結」 | この時点の計画がEVMの基準線（PV）。**EVMのための操作はこれだけ** |
| **実行（日々）** | | | |
| 08 | 外部ツールへ一括起票 | WBS「API起票」 | 後回し可。日々の進行は専門ツールで |
| 09 | 完了が自動で戻る | Webhook | 後回し可。連携しない場合はWBSで直接チェックすれば同じ |
| **月次（くり返す）** | | | |
| 10 | 前月の実績を確認して確定 | 月次実績 | 計画どおりの月は**何も入力しない**（未入力＝計画どおり） |
| 11 | 締める | 月次実績（管理職） | 締めた月は変更不可。解除は理由必須で履歴が残る |
| 12 | 報告する | プロジェクトサマリー／ダッシュボード／レポート | 1案件はサマリー、全体はアラートセンター、対外提出はCSV |
| 13 | ズレていたら調整して計画へ戻る | プロジェクト「商流」→ WBS「計画を凍結」 | 変更請求を承認すると受注額・納期に反映。再凍結して④へ戻る |

> **最初の1案件では、どこまでやるか**
>
> 13ステップ全部を初回からやろうとすると力尽きます。
> **①②③と⑩⑫だけ**——人を入れて、案件を登録して、粗いWBSで概算を出し、月に1回だけ実績を見る。
> これでも「誰にどれだけ乗っているか」「予算に対してどうか」は見えます。
>
> ④〜⑦（精緻化と凍結）はEVMを使いたくなってから、
> ⑧⑨（外部ツール連携）は手作業がつらくなってからで間に合います。

## 7. 導入の段取り

ここまでは**案件1本の流れ**でした。最後は、それを**組織に入れていく順番**です。

一度に全部やろうとすると挫折します。この順番を推奨します。

### ステップ1: 触ってみる（30分）

デモデータを入れて、画面を一通り見ます。まだ自分のデータは入れません。

### ステップ2: 1案件だけ入れる（半日）

一番よく分かっている案件を1つ選び、WBS・体制・予算を入れます。
既存のCSVがあれば、[管理画面のCSV一括登録](admin.md)でまとめて取り込めます
（メンバー／プロジェクト・タスク／アサインの3種。テンプレートをダウンロードできます）。

**この段階では予実を追わなくて構いません。** 計画が入るだけで、
「誰にどれだけ乗っているか」は見えるようになります。

### ステップ3: 月次のリズムを作る（1〜2ヶ月）

月に1回、実績を確認して確定させる場を作ります。
最初は精度を求めず、**続けること**を優先してください。

| タイミング | やること |
| --- | --- |
| 月初 | 前月の実績をレビュー → 修正 → 確定 |
| 月次処理後 | 管理職が締める |
| 随時 | ダッシュボードのアラートセンターを確認 |

### ステップ4: 広げる

1案件で回るようになったら、案件を増やします。
このあたりから、複数案件を横断した山積み・部門予算の予実が効いてきます。

外部ツール連携（API起票・完了同期）は、**手作業がつらくなってから**で構いません
（[外部ツール連携](integration.md)）。
