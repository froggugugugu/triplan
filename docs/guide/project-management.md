## この文書について

プロジェクトの管理を任されたけれど、何をどう見ればいいのか分からない——という方に向けた入門です。
**ツールの操作は出てきません**。管理という仕事が何をするものなのかを先に掴んでから、
[triplanの使い所](concept.md) と [利用ガイド](index.md) へ進んでください。

---

## 1. プロジェクトとは何か

プロジェクトは、**終わりがあって、一度きりで、目的がある**仕事です。

| | プロジェクト | 定常業務 |
| --- | --- | --- |
| 終わり | ある（納期） | ない（続く） |
| 内容 | 毎回違う | 毎回同じ |
| 体制 | 都度組む | 固定 |
| 例 | 基幹システムの刷新、新サービスの立ち上げ | 問い合わせ対応、月次の締め処理 |

この「一度きり」が厄介です。同じことを繰り返す仕事なら、慣れれば精度が上がります。
プロジェクトは毎回条件が違うので、**前回うまくいったやり方がそのまま通じません**。
だから、勘ではなく事実を見ながら進める必要があります。それが管理です。

---

## 2. なぜ管理が要るのか

管理をしないとどうなるか。よくある光景です。

> 3ヶ月で作る約束のシステム。1ヶ月経って進捗を聞くと「だいたい8割です」。
> 2ヶ月目も「8割です」。3ヶ月目、納期の1週間前に「間に合いません」と言われる。

ここで起きているのは、**遅れたこと**ではありません。
遅れが**分かるのが遅すぎたこと**です。

1ヶ月目の時点で「本当は3割」と分かっていれば、打つ手はいくつもありました。
納期1週間前に分かったのでは、もう何もできません。

**管理の目的は、失敗を防ぐことではなく、問題に気づく時期を早めることです。**
早く気づけば選択肢が残っている。遅く気づくと選択肢が無い。それだけの違いですが、
結果はまるで変わります。

## 3. QCD ── 守るべき3つの約束

プロジェクトが約束しているものは、突き詰めると3つです。

| | 何を約束したか | 言い換えると |
| --- | --- | --- |
| **Q**uality | 品質 | 何を、どこまで作るか |
| **C**ost | コスト | いくらで作るか |
| **D**elivery | 納期 | いつまでに仕上げるか |

製造業から来た「QCD」という言葉ですが、システム開発でもそのまま通じます。
英語圏では**鉄の三角形（Iron Triangle）**と呼ばれます。

### 3つ同時には良くできない

これが最も大事な性質です。

```
            Q（品質・スコープ）
                  ▲
                 ╱ ╲
                ╱   ╲
               ╱     ╲
              ╱       ╲
             ▼─────────▼
    C（コスト）     D（納期）

    どれか1つを動かすと、必ず他のどれかが動く
```

- **納期を早めたい** → 人を増やす（コスト増）か、機能を削る（品質・スコープ減）
- **コストを下げたい** → 機能を削る（品質・スコープ減）か、期間を延ばす（納期後ろ倒し）
- **機能を増やしたい** → コストが増えるか、納期が延びる

「全部やる」は選択肢ではありません。**どれを優先し、どれを譲るか**を決めるのが
プロジェクトの意思決定です。

> **品質を落とすという選択肢について**
>
> 3つのうち、品質だけは扱いが違います。テストを削る・レビューを飛ばすといった形で
> 短期的には納期とコストを縮められますが、その分は不具合対応として後から必ず返ってきます。
> 品質を「下げる」のではなく、**作る範囲（スコープ）を絞る**のが健全な調整です。
> ここでいうQは「作らないものを決める」ことだと理解してください。

## 4. 人・モノ・金 ── 動かせる3つのレバー

QCDは「守るべき約束」でした。では、その約束を守るために何を動かすのか。
手元にあるのは3つです。

| | 何を持っているか | 具体的には |
| --- | --- | --- |
| **人** | 体制 | 誰が、どれだけの稼働で、いつまで関われるか |
| **モノ** | 成果物 | 何を作るか、どこまで作るか、どの順で作るか |
| **金** | 予算 | いくらまで使えるか、いくら受注しているか |

QCDと人・モノ・金は、こういう関係にあります。

```
    【守る約束】   Q 品質・スコープ    C コスト      D 納期
                        ▲               ▲            ▲
                        │               │            │
                 ┌──────┴───────┬───────┴─────┬──────┴──────┐
                 │              │             │             │
    【動かすレバー】  モノ（成果物）    金（予算）      人（体制）
```

ただし、**レバーとQCDは1対1では対応しません**。1つ引くと複数が動きます。

- **人を増やす** → 納期は縮むかもしれないが、コストは確実に増える。
  しかも増えた人が戦力になるまで時間がかかり、教える側の手も止まる
  （*人月の神話*: 遅れているプロジェクトに人を足すと、さらに遅れる）
- **機能を削る** → コストも納期も縮むが、発注元との合意が要る
- **予算を増やす** → 人を足せるが、そもそも増やせないことの方が多い

この「引くと連動する」性質があるから、**3つを別々に管理しても意味がありません**。
人だけ見ても、金だけ見ても、判断はできない。同時に見て初めて「どのレバーを引くか」を選べます。

### 日本のシステム開発では、金が先に決まる

商習慣として、多くの案件は**予算が先に確定**します。
「1,000万円で、この機能を、3月末までに」という形で発注が来る。

つまり **C（コスト）は動かせない前提**で始まることが多い。
すると調整に使えるのは実質「モノ（作る範囲）」と「D（納期）」だけになります。

だからこそ、**予算が常に見えていること**が決定的に重要です。
予算が見えていないと、この調整判断ができません。
そして気づいたときには予算が尽きていて、開発側に無理が押し付けられる——
という流れが繰り返されます。

## 5. 管理の基本サイクル

やることは、突き詰めると4つの繰り返しです。

```
  ①計画を立てる  →  ②実行して記録する  →  ③計画と実績を比べる  →  ④調整する
        ↑                                                              │
        └──────────────────────────────────────────────────────────────┘
```

### ① 計画を立てる

**大きな仕事を、見積もれる大きさまで分解する**ところから始めます。
これを WBS（Work Breakdown Structure ／ 作業分解構成図）と呼びます。

```
基幹システム刷新
├─ 要件定義
│   ├─ 業務要件のヒアリング     … 10人日
│   └─ 要件定義書の作成         … 15人日
├─ 基本設計
│   ├─ 画面設計                 … 20人日
│   └─ データベース設計         … 10人日
└─ 実装・テスト
    └─ …
```

分解の目安は「**1つが数日〜2週間程度で終わる大きさ**」です。
大きすぎると見積もりが当たらず、進捗も「だいたい8割」になります。
細かすぎると管理そのものが仕事になります。

分解できたら、それぞれに **工数**（何人日かかるか）を見積もり、
**誰がやるか**（体制）と **いつやるか**（スケジュール）を決めます。

### ② 実行して記録する

計画どおりに進むことはまずありません。だから記録します。

記録するのは2つだけです。

- **どこまで終わったか**（進捗）
- **どれだけ使ったか**（実績工数・実績コスト）

ここで挫折しがちなのは、記録が面倒だからです。
**続かない記録は無いのと同じ**なので、粒度は割り切ってください。
毎日でなくてよい。月に1回でも、事実が残っていれば判断できます。

### ③ 計画と実績を比べる

管理で最も価値があるのに、最もサボられるのがここです。

見るのは3つの数字です。

| | 意味 | 例 |
| --- | --- | --- |
| **予定していた分**（PV） | この時点までに終わっているはずの量 | 500万円分 |
| **実際に終わった分**（EV） | この時点までに実際に終わった量 | 300万円分 |
| **実際に使った分**（AC） | この時点までに実際にかかった費用 | 600万円 |

この3つを並べると、状況が一目で分かります。

- 終わった分（300）＜ 予定（500） → **遅れている**
- 使った分（600）＞ 終わった分（300） → **お金を使いすぎている**

上の例は「予定の6割しか進んでいないのに、予算は6割以上使った」状態です。
このままいけば大幅な赤字と遅延になります。**今なら手を打てます。**

この考え方を EVM（Earned Value Management ／ 出来高管理）と呼びます。
名前は難しいですが、やっていることは「予定・実績・出来高の3つを並べる」だけです。

### ④ 調整する

差が見つかったら、レバーを引きます。第4節で見たとおり、選択肢は限られています。

- 作る範囲を絞る（発注元との合意が要る）
- 納期を延ばす（同上）
- 人を足す（コストが増える／すぐには効かない）

どれも痛みを伴いますが、**何もしないのが一番高くつきます**。
そして調整するたびに計画を引き直し、①に戻ります。

> **計画は「守るもの」ではなく「比べるもの」です。**
> 計画どおりに進まないのは失敗ではありません。計画と実績を比べられないことが失敗です。

## 6. よくある失敗と、その処方箋

| 失敗 | 何が起きているか | 処方箋 |
| --- | --- | --- |
| **進捗が「だいたい8割」のまま動かない** | タスクの粒度が大きすぎて、終わったかどうか本人にも分からない | 数日で終わる大きさまで分解し、**終わった／終わっていない**の2択で数える |
| **遅れの発覚が遅い** | 計画と実績を比べていない。聞かれたときだけ感覚で答えている | 月に1回でよいので、予定・実績・出来高を並べる場を作る |
| **予算が見えないまま進む** | 予算の担当と開発の担当が分かれていて、数字が突き合わされていない | 使った額と残額を、開発側が常に見える場所に置く |
| **担当者の頭の中にしかない** | 体制・配分・経緯がExcelや記憶に散っている | 誰がどの案件に何割いるかを1箇所に集める |
| **人を足して余計に遅れる** | 立ち上げの説明コストと、増えた分のコミュニケーションコストを勘定していない | 遅れの原因が人手不足かを先に確かめる。多くの場合は違う |
| **「終わったこと」にして次へ進む** | 完了条件が曖昧で、後から手戻りが発生する | タスクごとに「何ができたら完了か」を先に書く |

## 7. 未経験なら、まずこれだけ

全部やろうとすると続きません。優先順にこの3つから始めてください。

### ① 作業を分解して、完了条件を書く

「要件定義」では大きすぎます。「業務要件のヒアリング（完了条件: 議事録を関係者が承認）」まで割る。
完了条件が書けないタスクは、まだ分解が足りていないサインです。

### ② 誰がどれだけ関わるかを数字にする

「Aさんは今月このプロジェクトに0.5人月（＝半分の時間）」という形で書き出します。
これをやると、**1人に1.5人月ぶんの仕事が乗っている**といった無理がすぐ見えます。

### ③ 月に1回、予定と実績を並べる

完璧な精度は要りません。「予定より遅れているか、進んでいるか」が分かれば十分です。
これを月次で繰り返すだけで、納期1週間前に驚くことはなくなります。
