## この画面で何ができるか

「見積」画面（サイドバー「計画」→ 見積、またはプロジェクト一覧の行アイコン）は、
**1つの案件について、見積を段階ごとに記録して、後から実績と比べる**ための画面です。

- **記録**: 引合の超概算 → 受注時のWBS → 要件確定後のWBS → 完了時の実績、と版を積む
- **コーン**: 段階ごとの見積と「実績が収まる幅」を1枚のグラフで見る
- **振り返り**: どの段階の見積がどれだけ外れたか。次の見積に使う「人時/FP」の実績値

WBSの概算予算（工数 × 概算単価 × 係数）はWBS画面が出します。見積画面はそれを**否定しない**、
その前後を補う画面です。WBSがまだ無い引合の時点で数字を出す手段（簡易FP）と、
WBSを切ってからの見積を「いつの段階の見積か」つきで残す手段を足しています。

## 不確実性コーン（Cone of Uncertainty）

見積の誤差は「分かっていること」が増えるほど狭まります。これは手法の良し悪しではなく、
**まだ決まっていないことが減るから**です。出典（Boehm 1981／McConnell 2006）の値をそのまま使います。

| 段階 | 実績÷見積の幅 | 日本のSI案件での目安 |
| --- | --- | --- |
| 初期コンセプト | 0.25x〜4x | 話が来た直後 |
| 製品定義の承認（提案・受注） | 0.5x〜2x | 提案・受注。**受注時にWBSを切っても要件が固まる前ならここ** |
| 要件定義完了 | 0.67x〜1.5x | 要件定義書の合意 |
| 基本設計（UI設計）完了 | 0.8x〜1.25x | |
| 詳細設計完了 | 0.9x〜1.1x | |
| 完了（実績） | 1x | |

「受注時にWBSを切っているのに幅が2倍もあるのはおかしい」と感じるかもしれませんが、
コーンの主張はまさにそこです。WBSを切っても、知っていることが増えていなければ幅は狭まりません。
受注額と見積の間には、その幅のぶんだけ余地が要ります（要らないなら、要件を先に固めるのが筋です）。

## 簡易ファンクションポイント（NESMA）

WBSを切る前に金額を出すための、**数えるだけ**の方法です。複雑度は評価しません
（引合段階で複雑度まで見積もるのは偽精度です）。

| 方法 | 数えるもの | 重み | 使いどころ |
| --- | --- | --- | --- |
| 概算法 | ILF（内部論理ファイル）・EIF（外部インタフェースファイル） | ILF×35、EIF×15 | データの塊しか分からない引合初期 |
| 推定法 | 上記＋EI（外部入力）・EO（外部出力）・EQ（外部照会） | EI×4、EO×5、EQ×4、ILF×7、EIF×5 | 画面・帳票の一覧が挙がる提案段階 |

### 数え方の目安

- **ILF**: このシステムが**自分で持って更新する**データの塊（顧客、受注、請求…）。
  テーブル1つではなく「業務上ひとまとまりのデータ」で数える
- **EIF**: **他システムが持っていて参照だけする**データ（会計の勘定科目、人事の社員マスタ…）
- **EI**: データを**入れる**画面・取込（登録・更新・削除の画面、CSV取込）
- **EO**: **加工して出す**もの（集計帳票、計算結果つきの一覧）
- **EQ**: **そのまま出す**もの（検索して一覧を出すだけ、詳細表示）

同じ「顧客」でも、登録画面（EI）と一覧（EQ）と顧客データ（ILF）は別に数えます。

### 換算

```
合計FP   = Σ 件数 × 重み                          … 整数
人日     = 合計FP × 人時/FP ÷ 時間/日             … 小数2桁
人月     = 人日 ÷ 人日/人月                       … 表示のみ
万円     = 人月 × 概算単価 × 係数（案件別）        … 整数（WBS概算予算と同じ計算）
```

「人時/FP」は全社設定（管理画面 → 全社設定 → 見積・単価）で決めます。既定値の10は
ISBSG・IPAの公開データで業務系新規開発の中央値が概ね8〜15人時/FPの帯にあることから置いた
**暫定値**です。自社の完了案件が溜まったら、振り返りタブの「実績 人時/FP」の中央値を見て
寄せてください。記録は記録時点の設定値を凍結するので、後から設定を変えても過去の版の数字は動きません。

## 記録の運用

| いつ | 方法 | 段階 |
| --- | --- | --- |
| 案件の話が来た | 簡易FP（概算法） | 初期コンセプト または 製品定義 |
| 提案を出す | 簡易FP（推定法） | 製品定義 |
| 受注して初期WBSを切った | WBS積み上げ | 製品定義（要件未確定のため） |
| 要件定義で固まった | WBS積み上げ | 要件定義完了 |
| 基本設計・詳細設計の完了 | WBS積み上げ | それぞれの段階（任意） |
| 完了した | 実績 | 完了（自動） |

- **要件追加**は、商流ダイアログで変更要求（CR）を承認したあと、見積画面で新しい版を記録し、
  「変更要求との紐づけ」でそのCRを選びます。簡易FPなら「前回のFP項目をコピー」してから
  増えた機能を足すと、版の間で**どの機能が増えたか**が差分として残ります
- 記録は追記専用です。訂正は**最新版の取り消し**だけができます（途中の版を消すと連番と差分が壊れるため）
- 協力会社や他ツールの見積を写すときは「手入力」を使います

## 振り返りの見方

- **実績÷見積**: 1.0xより大きければ見積より実績が多かった。「幅の内側」なら、その段階として
  想定内の誤差です。**外側なら、その段階で「分かっていたつもり」のことが実は決まっていなかった**
  可能性が高い。次の案件では、その段階の見積に余地を持たせるか、要件を先に固めます
- **実績 人時/FP**: 実績の人日 × 時間/日 ÷ 最新のFP版の合計FP。全社設定の値と並べて表示します。
  完了案件が複数あれば「校正ヒント」に中央値が出ます
- 比較する実績は、完了時の記録（実績の版）があればそれを、無ければ現在の実績
  （アサインの実績優先の合算と実コスト）を使います
